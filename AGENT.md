# AGENT.md

## Repository rules

- Treat `scripts/patch-extension-*.mjs` as the maintained source for BMG changes to the upstream Edge extension. `extension/` is a generated, ignored runtime artifact and must not be committed.
- Rebuild the extension through `scripts/setup.ps1`; it verifies the pinned upstream archive SHA256 before applying BMG patches.
- Keep navigation behavior in `scripts/patch-extension-navigation.mjs`, content fallbacks in `scripts/patch-extension-web-content.mjs` / `scripts/patch-extension-content-cdp.mjs`, and do not duplicate responsibilities across patchers.
- Keep upstream public-tool targeting and record/replay workspace isolation in `scripts/patch-extension-upstream-tools.mjs`. BMG should expose the complete public tool catalog of the pinned `chrome-mcp-shared` version plus dynamic `flow.<slug>` tools; do not maintain duplicate upstream tool schemas in the sidecar.
- Append BMG-specific model guidance only to the relevant upstream tool description in `augmentWorkspaceTools`; preserve upstream names, input schemas, and descriptions for unrelated tools.
- Upstream tools that use active/currentWindow semantics must be converted to explicit BMG tab/window targeting before they are reachable through the public BMG endpoint. Dynamic flow tab/window creation, switching, lookup, and closing must stay inside the ownership-verified BMG workspace window.
- Reject public `chrome_close_tabs` in workspace mode before browser dispatch: the managed anchor tab must survive ordinary page cleanup. Internal idle cleanup may close only verified extra workspace tabs, keeping the anchor. Do not substitute a close that silently drops the BMG window.
- Give Edge bootstrap and ownership claim subprocesses a 60-second execution budget; the nonce claim's internal window search may wait up to 30 seconds. Keep unrelated ordinary show/hide/inspect operations at their own existing limits.
- Browser automation from local external consumers must go through `bmgctl`; do not read the approval secret or call private `/internal/*` endpoints directly.
- When MCP `tools/list`, public tool names, descriptions, or input schemas change, first deploy and validate the live Sidecar, then have the user select **Refresh tools** in ChatGPT plugin management. Restarting BMG alone cannot refresh ChatGPT's cached schema. Verify the refreshed tool list; only reconnect the app if refresh is unavailable or demonstrably fails.
- For an actual reconnection, give the user a private local PowerShell block that prints the public MCP URL from `BMG_RESOURCE` and the OAuth approval key stored at `BMG_APPROVAL_SECRET_FILE`. Prefer the README's absolute-path, direct-current-session form: do not wrap a block containing `$variables` inside an outer double-quoted `powershell.exe -Command "..."`, because the caller shell can expand those variables before the inner PowerShell receives them. BMG OAuth uses dynamic client registration + PKCE without a static client secret; "OAuth key" here means the approval secret entered on the consent page.
- Never execute that secret-printing command on the user's behalf, capture its output, read the approval-secret file, or paste the secret into chat. The user must run it locally and use the values themselves during reconnection.
- Preserve BMG workspace ownership checks. Never hide, show, move, close, or repurpose an Edge window unless its HWND/marker/process ownership has been verified.
- Workspace recovery must not be suppressed merely because unrelated Edge processes already exist. Recovery may launch a new nonce-marked bootstrap window, but it must not alter unverified Edge windows.
- While a bootstrap claim is still inside the 30-second startup grace window, recovery must reuse that pending claim instead of overwriting its state or launching another bootstrap window.
- After the startup grace expires, a pending bootstrap must be explicitly claimed, confirmed absent, or ownership-verified and retired before its state is replaced. Never create another bootstrap merely because the previous state is old, and never retire an entire Edge process to clean up a bootstrap HWND.
- Page automation is background-first. Keep window visibility and foreground activation distinct: `bmg_show_workspace` without arguments makes the owned BMG window visible without taking focus; pass `activate: true` only when the user explicitly asks to focus, activate, switch to, or bring BMG to the foreground. Merely asking to show/display the window is not a foreground request. Explicit `background: false` on supported page tools and the element picker are foreground actions.
- Non-activating workspace display must use Win32 `SW_SHOWNA (8)` and keep the existing maximized/normal state and geometry. The hide helper's minimized-window preparation is a distinct path; do not change it without validating minimized-to-hidden behavior.
- Record every owned workspace show/hide transition (including implicit maintenance), command acceptance, helper failure, Win32 visibility/style outcome, and taskbar API completion in the append-only `logs/bmg-window-transitions.jsonl`. Never log URL, page title, OAuth material, or ownership marker. A successful `AddTab`/`DeleteTab` COM return is not proof of the actual Explorer taskbar UI; keep that distinction explicit. Logging failures must not affect window operations.
- Keep the independent, passive 30-second port-12306 monitor and sanitized request/recovery events in `logs/bmg-upstream-diagnostics.jsonl`. Never probe with browser tools, force a recovery from a timer, or log URLs, page content, tool arguments, secrets, session IDs, ownership markers, or untrusted exception text. Windows process snapshots are machine-wide correlation hints only, not verified BMG process ownership or exit causes. Diagnostic failures must not change browser behavior.
- Log approved-owner tool failures in that same diagnostics file using fixed failure kinds, route, and numeric HTTP status only; do not log upstream response text, untrusted classifications, or frozen arguments. A consumed failed owner action must never be replayed automatically; its independently issued grant may still be valid.
- After every BMG maintenance or deployment, and especially after any process restart, perform and report a complete read-only live chain check before calling the service healthy: confirm the 18007 Sidecar health and listener/PID; confirm port 12306 is actually LISTENING with its own PID (not merely mentioned in configuration); verify the Sidecar-to-12306 connection and the passive upstream diagnostics; verify the ownership-checked BMG workspace is present; and make a harmless browser read via the local `bmgctl call` route to prove Edge extension/native messaging/tool dispatch works. Review Sidecar error logs and any new upstream errors. A healthy `/health` response, TCP listener alone, or unit tests alone never suffice. Report exact passing and failing layers and any test limitations.
- Release acceptance is a hard, all-or-nothing gate: **code committed**, **sidecar restarted**, **ports listening**, **OAuth reachable**, **browser connected**, and **end-to-end tools passed** are distinct states. Never describe a deployment as delivered, healthy, fixed, complete, or successfully accepted while any mandatory check failed, timed out, was skipped, or returned an uncertain outcome. A successful outer `bmgctl` JSON wrapper or HTTP 200 is insufficient: inspect the nested browser result's `isError` and semantic success. Fail closed on parse errors. Do not misreport a transient pass amid repeat failures as stable recovery.
- For every maintenance cycle, verify both `chrome_get_web_content` with `textContent: true` and `chrome_read_page` with default arguments **and** explicitly `depth: 0`, plus any tool name and exact meaningful argument set that previously failed or was affected by the change. Repeat failed cases after repair and show per-variant pass/fail; do not change, omit, or normalize arguments merely to turn a failure into a pass. One tool's success or a fallback result does not cancel another tool's failure. If a tool uses a fallback, report that route accurately and separately; a fallback must not be represented as the primary method working.
- If acceptance fails, preserve the incident as **not delivered / degraded** even when the Git commit and push succeed; isolate the faulty layer, fix and re-test it, or report the exact unresolved blocker and leave it marked incomplete. Never instruct the user to refresh a ChatGPT plugin schema as a substitute for a failing live browser health check. Record any pending schema refresh as an additional outstanding release step rather than claiming that new model instructions are already live in ChatGPT.
- A post-maintenance check must not change or recreate the upstream browser just to make the check pass: inspect listener/process state before using any workspace operation capable of demand-driven recovery, and do not perform a destructive browser action, alter existing tabs, or implicitly reinitialize Edge as a health probe. Any explicitly authorized corrective action must be narrowly scoped, recorded, and followed by the full acceptance gate. Never conceal an unresolved verification failure in a positive headline.
- Use the maintained `scripts/check-bmg-live.mjs` live-acceptance probe (and investigate its nonzero exit) in addition to unit tests: it checks both listeners, the public OAuth metadata, workspace ownership, nested MCP tool results and primary accessibility-tree reads with both default arguments and `depth: 0`, while withholding page content. A failed or skipped live probe blocks delivery; never adjust its required cases just to get a green check.
- Under CCM, run that gate through the trusted full-access `node.exe --test tests\live-acceptance.test.mjs` test entry point; the normal restricted token may be unable to spawn `netstat.exe` or `bmgctl`, and this restriction is a probe failure, **not evidence of a missing 12306 listener**. Never bypass a failed live gate by relying on its unit test or by assuming its host was unhealthy.
- Never restart 12306, Edge, Native Messaging, or the Sidecar merely to check health or as an indiscriminate recovery attempt. Before a necessary restart, establish which component is faulty and scope the operation to that component. Afterward rerun the complete live-chain check; if 12306 is not listening or a browser tool fails, preserve diagnostics, stop claiming the system is healthy, and investigate the cause before requesting approval for a targeted repair. Do not solve a missing upstream listener by repeatedly restarting the Sidecar or closing unrelated Edge windows.
- If a tool call temporarily shows the BMG workspace and then fails before a normal result is observed, best-effort true-hide that ownership-verified workspace on the failure path; maintenance failure must not replace the original tool/upstream error.
- Idle cleanup may only affect tabs in the ownership-verified BMG workspace window; ordinary Edge windows are out of scope.
- Idle cleanup must not proactively recover or launch Edge when the browser/upstream is offline. Browser recovery remains demand-driven so intentionally closing Edge does not cause a later idle timer to reopen it.
- Use `node.exe --test tests\sidecar.test.mjs` for the trusted full Node test run under CCM. Also run `git diff --check` before committing.
- Keep `README.md` synchronized with the current implementation and real validation status. Remove obsolete names and descriptions instead of retaining defensive legacy wording.
- Keep `assets/bmg-mcp-icon.png` as the manually uploaded BMG ChatGPT MCP plugin icon. Validate that it is a readable square PNG under 10,000 bytes; do not replace manual upload with an image URL or confuse it with another project's icon.
- When the repository has a remote, finish completed implementation work by committing and pushing the intended branch.

## BMG MCP approval and phone authorization

- Keep the accepted WCM semantics in the BMG Sidecar approval layer: timed, totp, either and off modes; independently frozen owner actions; a card-specific nonce; exact-ID timed grants; single-use owner execution; and policy-revision revocation. In either mode, phone code and card are independent alternatives, not cumulative requirements. BMG's grant covers all public BMG browser tools, not WCM devices.
- Keep the WCM-style fixed HTTPS `/bmg/unlock` one-tap webpage as a third independent entry in `either` mode, not another grant store or a global-policy bypass. Initial browser pairing consumes a fresh user-entered BMG TOTP **on the webpage**, never through ChatGPT; subsequent one-tap unlocks issue ordinary full-BMG timed grants. The model claims at most one pending webpage grant via no-argument `bmg_claim_web_unlock`; a webpage claim must not dispatch a frozen owner action. Unclaimed grants expire and are revoked after five minutes; claimed grants remain usable for their selected duration (1 minute to 7 days). Repeated taps while pending cannot multiply grants. A policy revision invalidates all outstanding grants and browser pairings.
- Pairing cookies must be `Secure`, `HttpOnly`, `SameSite=Lax` and valid at most 90 days; store only pairing-token hashes outside Git in `.state/bmg-web-browsers.json` (max eight). Keep an unpredictable CSRF cookie and matching form field, paired-browser gate and one-use TOTP verifier. Do not use mobile-browser Origin/Referer/Fetch-Metadata as the authorization gate, and do not introduce wildcard Funnel routes. The allowlist scripts must include only the exact `/bmg/unlock` path. Tests must use fake TOTP in isolated HTTP servers, never production codes or a production browser pairing.
- Every OAuth-protected public tools/call, including BMG workspace controls and dynamic flow tools, must pass the Sidecar approval gate before reaching the extension or local workspace handler. Strip approval_id before upstream dispatch. Reject JSON-RPC batch requests. The loopback-only, local-secret-protected bmgctl management path is separate.
- Keep app-only get_approval_status and resolve_pending_action, nonce and optional Host-session binding, card remount revalidation, display-only historical receipts, and non-replayable owner actions. Widget state is never authoritative. Failed ChatGPT continuation must not replay an approved action.
- In totp mode require a fresh user-provided phone code via bmg_unlock or an exact active grant ID; missing authorization fails closed without creating a card. In either mode, a missing grant creates a frozen action for a card; alternatively bmg_unlock issues a grant from a user-provided code for a caller-driven browser retry without dispatching the pending action. Do not activate phone mode before local pairing. The DPAPI CurrentUser seed lives in %LOCALAPPDATA%\BMG\secrets and belongs to the local BMG Controller account. Never use CCM/BMG to run manage-bmg-totp.ps1 with Init or ReadForRouter, or to display the production seed; only the user enrolls/validates the phone in a private local terminal.
- Keep the BMG phone-code-blocked fallback explicit in the browser-tool, `bmg_unlock`, and `request_approval` descriptions and in `either`-mode `approval_required` output: if the six-digit BMG authenticator code is redacted or a tool call is blocked, prompt the model to immediately render a card for the already-frozen browser action rather than repeatedly requesting codes. If no pending ID exists, obtain one via the intended unapproved browser call; never invent an ID or automatically approve. This is BMG authorization only, not a website login CAPTCHA/SMS flow. In `totp`-only mode, do not claim card fallback works.
- Before changing PowerShell TOTP confirmation logic, run scripts/manage-bmg-totp.ps1 -Action SelfTest through CCM. Test with synthetic secrets, never a production code. Policy mode/revision changes revoke all active grants and pending approvals.
- Approval-related public tool schemas and MCP resources require ChatGPT BMG **Refresh tools** after deployment and live acceptance; verify the new tool actually appears. Use the README's private OAuth URL/key recovery instructions only if reconnection proves necessary; never read the secret yourself.
